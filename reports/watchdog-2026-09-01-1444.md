### BUG-1 — `server.ts:1284-1296` — TOCTOU гонка в `handlePromoRedeem` без транзакции (новый, от промокодов 14:42)

```ts
// server.ts:1284-1296 handlePromoRedeem — 5 последовательных SQL без BEGIN
// 1284 promoRows = SELECT code,reward,max_uses,uses FROM magnum_promo_codes WHERE code= LIMIT 1
// 1288 if (uses >= maxUses) return 409            // stale read
// 1290 ex        = SELECT id FROM magnum_promo_redemptions WHERE user_id= AND code= LIMIT 1
// 1291 if (ex.length>0) return 409                // check без FOR UPDATE
// 1292 INSERT INTO magnum_promo_redemptions (user_id, code) VALUES (...)          // без уникальности!
// 1293 UPDATE magnum_promo_codes SET uses = uses + 1 WHERE code=                 // без WHERE uses < max_uses
// 1295 UPDATE magnum_coins SET balance = balance + reward WHERE user_id=
// 1297 INSERT INTO magnum_transactions (...)
// 1299 ensureNotification(...)
```

Четыре мутации + две проверки — вне транзакции. При двух параллельных `POST /magnum/api/promo/redeem {"code":"VIP42"}` оба пройдут `uses < maxUses` и `already redeemed` до любого `INSERT`, оба вставят `magnum_promo_redemptions` (нет `UNIQUE(user_id,code)` в `drizzle/schema.ts:155`), оба сделают `uses+1` (превысит `max_uses`) и оба начислят `reward`. Проверка `maxUses` — stale, защита только на приложении.

**Связанная схема:** `drizzle/schema.ts:155 magnumPromoRedemptions` без `unique(userId, code)` — БД не отклонит дубль; `magnumPromoCodes.uses` инкрементится без `WHERE uses < max_uses` — гонка превысит лимит. Тот же класс бага что и `magnum_mining_vault` (watchdog 14:27/14:36), копипаста паттерна.

Риск: двойное начисление монет (до `1420` за `VIP42`), `uses` уезжает за `maxUses`, промокоды становятся источником инфляции. `magnum_transactions` пишется дважды — аудит ломается.
